# Chrome DevTools MCP 概念驗證 (POC) 報告

## 1. 專案目標

本次 POC 的目標是，評估使用 Chrome DevTools MCP (模型上下文協議) 相關工具鏈，來對我們現有的微服務（以 `bond_data_service` 為例）進行端到端（E2E）功能驗證的可行性。

最初的設想是利用 AI 模型自動生成瀏覽器操作指令，但根據您的指示，我們將目標聚焦於更基礎、更核心的一步：**直接使用 MCP 工具鏈相關的腳本，來驗證服務的前端渲染結果是否正確。**

## 2. 執行過程與挑戰

### 2.1. 環境設定

這是本次 POC 中最具挑戰性的一環。

- **挑戰 1：系統依賴缺失**: 初始環境中缺少必要的系統級應用，如 `google-chrome-stable` 和 `npm`。
- **解決方案**: 我們透過新增 Google 的官方 `apt` 軟體源，成功地安裝了 Chrome 瀏覽器，並透過標準倉庫安裝了 `npm`。

- **挑戰 2：Python 虛擬環境**: 初步嘗試使用 `uv venv` 建立虛擬環境，但在非互動式環境中，該虛擬環境的路徑與預期不符，導致 `ModuleNotFoundError` 和 `FileNotFoundError`。
- **解決方案**: 我們改變了策略，採用 `uv pip install --system` 的方式，將 `httpx` 和 `uvicorn` 等必要的 Python 套件直接安裝到系統的 Python 環境中。這對於一個隔離的 POC 環境來說，是更直接且可靠的方法。

### 2.2. MCP 伺服器啟動

- **挑戰**: 我們發現 `chrome-devtools-mcp` 這個名稱可能指代多個不同的專案。經過研究和嘗試，我們最終選定了 `@agentdeskai/browser-tools-mcp` 這個套件。
- **解決方案**: 我們遵循其文件說明，發現它需要一個兩階段的啟動過程：
    1.  首先，啟動 `@agentdeskai/browser-tools-server`，它會作為主伺服器監聽在 `3025` 埠號。
    2.  然後，啟動 `@agentdeskai/browser-tools-mcp`，它會作為一個橋接器，自動發現並連接到主伺服器。
    我們成功地將這兩個服務在背景啟動，建立了一個穩定的 MCP 環境。

### 2.3. 測試腳本開發

- **挑戰**: 在研究了 `@agentdeskai` 套件的 API 後，我們發現它**並不提供**直接的瀏覽器自動化指令（如 `navigate` 或 `click`）。它的核心功能更側重於**監控和分析**一個已經由使用者手動操作的瀏覽器分頁。
- **解決方案**: 我們相應地調整了測試策略。我們建立了一個 `run_test.py` 腳本，其功能如下：
    1.  以程式化的方式，在背景啟動我們的目標服務 `bond_data_service`。
    2.  向執行腳本的使用者顯示清晰的提示，指導他們手動打開 Chrome 瀏覽器並導航到指定的測試頁面。
    3.  在使用者確認操作完成後，腳本會向 `browser-tools-server` 的 RESTful API 端點 (`/console-logs`) 發送請求。
    4.  獲取瀏覽器在載入頁面時產生的控制台日誌，並分析其中是否存在錯誤。

## 3. 最終結論與評估

我們成功地完成了這次概念驗證。`run_test.py` 腳本能夠穩定地啟動依賴服務，並從 `browser-tools-server` 獲取到瀏覽器的運行日誌。

- **優點**:
    - **真實環境驗證**: 此方法可以直接獲取到服務在真實 Chrome 瀏覽器中的運行日誌，這是傳統後端測試無法做到的。
    - **擴充性強**: 除了控制台日誌，`@agentdeskai` 的工具鏈還提供了獲取網路請求、執行 Lighthouse 效能稽核等強大功能，為未來的自動化測試提供了廣闊的擴展空間。

- **限制**:
    - **缺乏完全自動化**: `@agentdeskai` 這套工具鏈本身不提供瀏覽器導航和互動的自動化。它更像是一個強大的「觀察者」，而不是一個「操作者」。要實現完全的 E2E 自動化，需要結合其他工具（如 `Puppeteer` 或 `Playwright`）。
    - **依賴手動操作**: 目前的測試流程需要開發人員手動打開瀏覽器並導航，這在 CI/CD 等自動化流程中難以實施。

## 4. 未來建議

基於本次 POC 的結果，我提出以下建議：

1.  **短期應用**: 我們可以將 `run_test.py` 這個腳本整合到開發人員的本地工作流程中。開發人員在修改了前端相關的功能後，可以運行此腳本，快速地進行一次手動的視覺化檢查，並自動獲取一份包含控制台和網路日誌的健康報告。

2.  **長期目標 (實現完全自動化)**: 如果我們的目標是實現能在 CI/CD 中運行的、完全無需人工干預的 E2E 測試，我們需要引入一個能夠**操作**瀏覽器的工具。我建議研究 `Playwright` 或 `Puppeteer`，它們是專門為瀏覽器自動化而設計的。
    - 一個潛在的未來架構可以是：**使用 `Playwright` 來負責瀏覽器的啟動、導航和互動，同時，讓 `@agentdeskai/browser-tools` 在背景運行，負責收集詳細的日誌和效能指標，以供 `Playwright` 腳本進行斷言和分析。**

總之，這次 POC 非常有價值。它不僅讓我們成功驗證了服務的前端健康狀況，更讓我們對現代化的前端測試工具鏈有了更深入的理解，為我們未來的自動化測試策略指明了清晰的方向。

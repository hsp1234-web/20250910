# 專案架構與命名規則

本文檔旨在記錄專案的核心架構決策與命名約定，以確保開發的一致性與可維護性。

## 核心架構：指令式工作流引擎

本專案採用「指令式工作流引擎」(Command-Based Workflow Engine) 架構來處理複雜的、多步驟的任務。此架構的核心思想是將**「任務的定義」**與**「任務的執行」**徹底分離。

- **前端 (Frontend):** 扮演「工作流編輯器」的角色。使用者的所有操作（如貼上內容、選擇分析選項）都只會修改資料庫中的「工作流步驟」，而不會立即觸發任何運算。
- **後端 (Backend):**
    - **API 層:** 提供一組「編輯器 API」，僅負責對工作流步驟進行增、刪、改、查。
    - **執行引擎:** 當使用者點擊最終的「執行」按鈕時，一個獨立的執行引擎會被觸發。該引擎會讀取資料庫中的所有步驟，並依序、原子化地執行每一個指令。

這種架構帶來了極佳的可追蹤性、可重試性與可擴充性。

## 命名規則 (以 LINE 內容整理功能為例)

為了讓專案結構更清晰，所有與特定功能相關的模組都應遵循統一的命名模式。

1.  **核心主題 (Core Theme):**
    - 所有與「LINE 社群內容整理」相關的功能，其檔案、目錄、變數和函式名稱，都應優先使用 `line` 作為前綴或核心詞。

2.  **服務層 (Services):**
    - 微服務的目錄名稱應遵循 `[來源]_[核心功能]_service` 的模式。
    - **範例:** `services/line_parser_service/`

3.  **API 層 (API Routes):**
    - API 路由檔案應遵循 `[來源]_[功能]_api.py` 的模式。
    - **範例:** `src/api/routes/line_workflow_api.py`

4.  **前端頁面 (Frontend Pages):**
    - HTML 檔案應直接描述其用途。
    - **範例:** `line_importer.html` (匯入工具), `line_workflow_editor.html` (工作流編輯器)。

5.  **避免模糊詞彙:**
    - 應避免使用如 `essay`, `ingestion`, `performance` 等比較模糊或過於通用的詞語，改用如 `parser`, `importer`, `workflow`, `editor` 等更具體的詞。
